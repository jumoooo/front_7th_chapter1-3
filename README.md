테스트 전략을 세우기 전, 먼저 현재 진행 중인 프로젝트의 구조를 명확히 이해하는 것이 중요하다고 생각했습니다.
테스트 코드는 단순히 효율성을 위한 것이 아니라, 유지보수가 쉽고 장기적으로 안정적인 구조를 만드는 것이 핵심이라고 봤습니다.
이를 기반으로 다음과 같이 분석했습니다.

* App.tsx 내부에 컴포넌트로 분리될 부분이 많음
* 컴포넌트 간 상호작용 존재 여부 확인 필요
* 상호작용이 많을 경우 단위 테스트(Unit Test)만으로는 충분한 신뢰성을 확보하기 어려움
* 통합 테스트(Integration Test)를 통해 컴포넌트 간 연계를 검증하는 것이 프로젝트 특성상 더 적합
* 결과적으로 테스트 피라미드(Pyramid) 보다는 테스트 트로피(Trophy) 구조가 프로젝트에 더 어울림

물론 프로젝트 규모가 크지 않기 때문에, 단위 테스트 중심의 피라미드 전략도 고려할 수 있었습니다.
하지만 추후 컴포넌트가 세분화되고 상호작용이 많아질 가능성을 생각했을 때, 단위 테스트만으로는 유지보수에 한계가 있을 것이라 판단했습니다.
따라서 트로피형 테스트 전략을 선택했습니다.

하지만 이 접근에는 두 가지 문제점이 있었습니다.

* 모든 컴포넌트를 나누는 작업에 시간이 걸림
* 상태 관리 로직을 분리했을 때, 예상 결과(expected value)를 일관성 있게 관리하기 어려움

## 과제 셀프회고

이번 과제에서는 테스트 전략을 수립하고 수정하는 과정에서 팀 내 논의가 가장 많은 시간을 차지했습니다.
약 3일간 코어 타임 동안 하루 4시간 이상을 회의에 투자했는데, 그만큼 테스트 구조와 방향성에 대한 고민이 깊었습니다.

특히 통합 테스트를 처음에는 “여러 기능을 묶어서 검증하는 테스트” 정도로 단순하게 생각했지만,
막상 실제 구현 단계에서 **“어떤 기준으로 파일을 나누고, 어떤 범위를 통합 테스트로 볼 것인가”**를 정하는 일이 예상보다 훨씬 어렵다는 걸 느꼈습니다.
이 과정을 통해 단순한 테스트 작성이 아니라, 테스트 아키텍처를 설계하는 사고방식을 배울 수 있었습니다.


### 테스트 코드 3주간의 회고

이번 3주간의 테스트 코드 학습은 단순히 “테스트를 배우는 과정”을 넘어, AI와 함께 개발하는 환경을 이해해 가는 과정이었다고 느꼈습니다.
처음에는 테스트 코드 과목이라 해서 검증 절차나 코드 품질 향상에만 초점을 맞출 줄 알았지만, 되돌아보면 AI와 협업하기 위한 개발 기반을 다지는 과정이었던 것 같습니다.

AI Agent를 본격적으로 다룬 것은 2주차부터였지만, 그 이전 1주차에 테스트 코드의 개념과 구조를 익히는 과정이 결과적으로 AI 개발 워크플로우의 매뉴얼을 설계하는 데 중요한 역할을 했습니다.
특히 3주차에는 Storybook과 Chromatic을 연동하고, E2E 및 통합 테스트를 진행하면서 시각적으로 결과물을 확인했는데, 이 경험을 통해 AI가 생성한 결과물을 검증하고 신뢰할 수 있는 체계를 만드는 것이 테스트의 본질이라는 점을 깨달았습니다.

제 생각은 이번 과정을 이렇게도 정리할 수 있을 것 같습니다:

* 1주차: AI가 코드 작성 시 참고할 수 있는 명확한 규칙과 테스트 구조를 학습
* 2주차: AI Agent의 작동 원리와 협업 방식 이해, 자동화된 작업 구조 설계
* 3주차: 위 과정을 기반으로 실제 기능 개발 및 E2E·통합 테스트 수행, Chromatic을 통한 시각화와 결과물 배포

이렇게 생각하면 이번 학습은 AI가 만든 결과물을 사람이 신뢰할 수 있도록 검증하는 과정이었고,
단순히 테스트 코드만 배우는 것이 아니라 AI와 공존하는 개발자로서 어떤 사고방식을 가져야 하는지 고민할 수 있는 시간이었습니다.
저는 “AI가 만든 결과를 사람이 어떻게 신뢰할 수 있을까”에 대한 탐구 과정이었다고 생각합니다.

앞으로는 테스트 코드를 “품질 관리 도구”로만 보지 않고,
AI 협업 환경에서 개발 프로세스를 안전하게 유지하는 핵심 도구로 인식하고 더 깊이 있게 공부해 보고 싶습니다.

### 기술적 성장

이번 과제에서는 가능하면 AI 도구에 의존하지 않고, 실제 테스트 코드 작성 과정 자체를 익히는 데 집중했습니다.
물론 이전에 사용했던 프롬프트나 설정들은 일부 사용했지만, 대부분은 직접 작성하며 문제를 해결하는 방식으로 진행했습니다.

Cursor를 활용해 폴더 구조와 주석 기반의 테스트 설계 틀을 먼저 만들고, 그 위에 수동으로 테스트를 작성했습니다.
필요할 때만 AI의 도움을 받아 Playwright나 Storybook 등 테스트 도구의 동작 원리와 실무 적용 방식을 직접 학습했습니다.

비록 회의로 인해 실습 시간이 부족했지만,
과정 중 배운 테스트 설계 패턴과 작성 노하우를 추후 재사용할 수 있도록 Notion에 복기 및 정리할 계획입니다.
이 경험을 통해 단순히 “코드를 짜는 사람”이 아니라, 테스트 전략을 이해하고 설계할 수 있는 개발자로 한 단계 성장했다고 느꼈습니다.

### 코드 품질

1주차에 비해 이번 과제에서는 테스트 코드 작성 과정이 훨씬 자연스러워졌습니다.
특히 Mock 데이터 구분, DOM 요소 접근 방식, 그리고 테스트 대상의 상태를 추적하는 로직 등에서 시행착오가 줄었습니다.

또한 이전에 작성한 테스트 코드를 기반으로 공통 로직을 재사용할 수 있는 구조를 잡으면서 생산성이 향상되었습니다.
테스트 간 중복을 줄이고, 유지보수를 고려한 코드 설계의 중요성을 다시 한 번 체감했습니다.

아직 컴포넌트 단위의 테스트 구조가 완벽히 정돈된 것은 아니지만,
테스트 코드가 점점 **‘읽히는 코드’**로 발전하고 있다는 점이 개인적으로 만족스러웠습니다.

### 학습 효과 분석

* Playwright와 Storybook 등 브라우저 기반 E2E 테스트 도구의 기본 사용법 및 동작 구조 이해
* E2E 테스트와 통합 테스트의 차이점과 목적의 명확한 구분
* 통합 테스트 파일을 어떻게 분리해야 유지보수성과 협업 효율을 높일 수 있는지에 대한 고민
* 이론적으로 완벽한 테스트 전략보다는, 팀의 현실적인 작업 시간과 리소스에 맞는 전략이 더 효과적일 수 있다는 인식
* 테스트 작성 과정이 단순히 품질 보증이 아닌, 개발 구조 개선의 일환이라는 시각
